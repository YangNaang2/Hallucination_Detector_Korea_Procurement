너는 ko-LettuceDetect / ASTRA의 생성 모델 비교 평가 엔지니어다.
나는 이 프로젝트를 처음 전달한다. 이 폴더는 모델 평가 담당자 한 명에게 전달하는 개발·평가 패키지다.
목표는 동일한 300질문을 Llama·Qwen·EXAONE 계열의 실제 이용 가능한 모델로 실행하고, 공통 기준에 따른 비교 결과를 만드는 것이다.

1. 먼저 실제 파일을 읽고 검증해라.
README.md, metrics.md, experiment_plan.json, PACKAGE_MANIFEST.json을 먼저 읽고 python validate_package.py를 실행해라.
project-docs/평가데이터/v2/evaluation/questions_300.jsonl 및 CSV, 51건 통합 요건시트와 재확인 결과, 가상기업/v1 마스터·생성 문서, v2 시나리오·retrieval_manifest, 기존 procurement-pipeline RAG 코드와 README를 확인해라.
기존 baseline/은 실제 과거 답변을 따로 모은 참고 자료다. 300개 레코드 중 생성295·접근차단5이며 일부 검색 수정과 재실행 조건이 섞였다. 단일 조건의 모델 정확도라고 보고하지 마라.
기존 팀원4명의 25문항 검수도 참고하되 최종 승인 pending을 gold 확정으로 바꾸지 마라.

2. 데이터와 시스템을 구분해라.
51행 요건시트는 공고 조건을 구조화한 검토 자료이며 RAG 원문 청크 그 자체가 아니다.
L1은 실제 공개 공고, L2/L3는 가상 회사의 내부·민감 자료다. 회사5곳과 합성 시나리오가 있으므로 공개 공고만으로 모든 질문을 풀 수 없다.
기대답·reasoning·must_include·must_not_claim·판정·과거 실제 답변·검수 의견은 평가 전용이다. 모델 입력이나 검색 코퍼스에 넣지 마라.
private_audit_evidence는 관리자 검수 전용이며 접근차단 요청에 대한 응답·생성 컨텍스트로 사용하지 마라.
기존 300문항·기대답·회사·원본 결과를 덮어쓰지 마라. 오류를 발견하면 별도 errata와 영향 문항을 기록해라.

3. 실행 환경을 먼저 점검해라.
현재 PC의 OS·CPU/GPU·RAM/VRAM·디스크·기존 런타임과 모델 파일을 확인해라.
Llama/Qwen/EXAONE은 후보 계열이지 설치 완료 모델이 아니다. 공식 모델 카드와 런타임 지원을 확인하고 정확한 ID·revision·양자화·라이선스·모델 크기를 고정해라. 사용자 대신 라이선스에 동의하지 마라.
가능하면 유사 파라미터 규모·양자화·컨텍스트 정책의 비교군을 선택하고, 맞출 수 없으면 차이를 표기하고 모델 계열 자체의 우열로 일반화하지 마라.
외부 유료 API·모델 학습·전체 재다운로드는 자동으로 하지 마라. 대용량 설치 필요 시 크기와 디스크·자원 확인 후 판단하고 새 환경을 분리해라.
원천·색인 파일이 없으면 SOURCE_TRANSFER.md의 전달 방식을 확인하고 실제 필요한 경로·자료를 구체적으로 요청해라. 파일이 없는 상태를 완료로 보고하지 마라.

4. 공통 비교 조건을 확정해라.
우선 metrics.md의 fixed-retrieval 트랙으로 검색 근거를 질문별 한 번 동결하고 생성 모델만 교체해라.
질문·공고차수·회사·tenant·역할·시나리오버전·기준일, 근거 ID·순서·텍스트·해시를 고정한다. 모든 모델에서 들어가는 공통 근거 길이를 사전 검증해라. 모델별로 다른 근거를 몰래 삭제하거나 변경하지 마라.
서버 ACL을 검색 전에 적용하고 반환 직전 재검증한다. 다른 회사·권한 밖 등급·다른 시나리오를 혼입하지 마라. 기존 context_qa300 및 rag_pilot 코드를 우선 활용해라.
같은 system prompt·질문·출력 요구·샘플링 정책을 사용하되 모델별 공식 chat template 및 thinking 설정을 기록한다. seed 고정만으로 비트 단위 재현을 보장한다고 하지 마라.
원천이 없어 인용만으로 실행하면 curated-reference 진단 트랙으로 명시하고 검색 성능을 주장하지 마라. 답변·판정 필드를 제거한 허용 업무 근거만 입력한다.
선택 모델·공통 조건·rubric은 결과를 보기 전에 새 버전으로 저장한다. 모델별 별도 채점표를 만들지 마라.

5. 소수 실행 후 전체로 확대해라.
회사와 주요 유형을 아우르는 소수 질문으로 먼저 요청·생성·근거·권한·출력 파싱을 검증한다.
수정은 해당 코드와 새 실험 버전에서 하고 기준 데이터는 유지한다. 사전검증에 사용한 질문과 조정 내역을 표시한다.
이후 모델별 전체300개 실행 슬롯을 처리한다. 정상 차단5개는 LLM 미호출이 원칙이며, 모델별 생성 요청은 기본295개다. 추가 오차단·실패가 있으면 실제 건수로 보고한다.
세 후보가 모두 준비되면 총900개 실행 슬롯, 기본 최대885개 생성 대상이다. 연결 상태나 자원상 불가능한 후보는 제외 이유를 남긴다. 없는 모델 결과를 만들어 채우지 마라.
질문별로 즉시 결과 저장, 중단 후 재개, 설정 해시 일치 검사, 재시도 attempt 분리, 실패 포함 집계를 구현해라. 좋은 답이 나올 때까지 반복하고 최고 답만 고르지 마라.
기존 baseline 답변을 새 모델 결과로 재사용하지 마라.

6. 실행 기록과 채점 코드를 실제 만들어라.
run_id, model_id/revision, runtime, quantization, hardware, seed, prompt_version/hash, context_snapshot/hash, sampling, question_id, status, attempts, actual_answer, finish_reason, references, timing, usage, error를 기록한다.
정본 답변은 그대로 보존하며 formatting 버전과 offset 단위를 명시한다. 문서·청크·정확한 인용·원본 정본 offset을 유지한다.
TTFT·생성시간·검색시간·전체시간·로드/워밍업 시간을 구분한다. 측정하지 않은 값은 null이다.
metrics.md의 v1을 공통 적용하고 질문별 판단 이유·문제 구절·근거를 함께 남긴다. 자동 규칙 검사와 에이전트 의미 검토와 사람 승인은 분리한다.
분모·N/A·미채점·오류·잘림을 노출하고, 회사별·유형별·기대동작별 분포와 paired 비교를 만든다. exact-match나 키워드 점수만으로 의미 정답률을 보고하지 마라.
추가 지표는 v2 별도 표로 관리하고 모든 모델에 동일하게 적용해라. 구절 F1은 신규 정본 답변에 승인된 gold가 있을 때만 계산해라.
과거25개 답변의 라벨 좌표를 다른 모델의 새 답변에 옮기지 마라. Llama/Qwen/EXAONE 생성 모델 비교와 KLUE/XLM-R/BGE-M3 환각 탐지기 비교는 다른 실험이다. 기본 생성 비교에 탐지기의 성능을 혼합하지 마라.

7. 검증해라.
300ID 유일성, 회사별60, 51공고 포함, 기대동작 분포, 파일 해시, 근거 위치, ACL·시나리오 경계, 평가 정답 유입 차단을 검사한다.
모델 이름 위장, 다른 질문 응답, 잘못된 인용, VAT 오류, 실패 누락, 권한 누출, 근거가 달라진 비교, 응답 캐시 혼용, 설정 다른 재개에 대한 의미 있는 오류 주입 테스트를 수행한다.
기존 train/dev/test를 보존하고 조정에 노출된 데이터는 독립 평가라고 하지 마라. 300개 전체 보고서는 개발 벤치마크로 설명해라.
모델 간 차이를 유의미한 성능 향상으로 주장하려면 표본·분할·장비·통계 근거를 추가로 확인해라.

8. 납품
실행 가능한 코드, 실행·재개 절차, 실제 모델 설정, 동결 입력 manifest, 모델별 결과JSONL, 공통 채점 결과, 비교표, 검증 기록, 남은 문제를 새 results/<experiment_version>/에 남겨라.
모델·원천·전체 파싱/프롬프트 캐시·키는 제출 ZIP이나 Git에 포함하지 마라. 관리자 평가 파일은 공개 UI 폴더에 넣지 않는다.
Git이 있으면 별도 작업 브랜치에 커밋하고 PR로 제출하되 main에 합치지 마라. ZIP 작업이면 수정 파일과 신규 결과·보고서를 하위 폴더 구조를 유지해 반환해라.
확인 가능한 정보를 다시 묻지 말고 자율 진행하되, 실제 원천 이전·라이선스 동의 등 해결되지 않는 항목만 구체적으로 요청한다. 그동안 독립 가능한 코드·검증을 완료해라.
완료 보고는 실제 실행 모델, 생성/차단/실패 수, 공통 지표, 사람 검수 필요 범위, 결과 위치와 다음 단계로 정리해라.
