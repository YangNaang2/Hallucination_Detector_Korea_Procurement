## 1. 가장 최근 확정한 프로젝트 정의

**입찰 참여 기업의 직원이 나라장터 공개 공고와 자기 회사 내부 자료를 함께 검토하고, AI 답변의 근거와 환각 의심 구간을 확인하는 서비스.**

주 사용자는 발주기관이 아니라 입찰·제안·사업 담당자다. ‘한빛IT’는 설명용 가상 입찰 기업이다.
한빛IT 직원은 한빛IT 자료만 볼 수 있고 다른 기업 직원은 자기 기업 자료만 본다. 공개 공고는 공동 이용할 수 있다.

| 등급 | 의미 | 예시 |
|---|---|---|
| L1 | 공개 공고 자료 | 입찰공고·제안요청서·과업지시서·규격서·정정공고 |
| L2 | 입찰 기업 내부 자료 | 과거 실적·보유 인증·소속/투입 가능한 인력의 경력·자격·장비 |
| L3 | 입찰 기업 민감 자료 | 원가·내부 단가·협력사 견적·투찰 예정가·수주 전략 |

**L2/L3는 3D 건물/내부 설비 단계가 아니다.** 과거 가상세계 지시문과 일부 UI에는 공간 단계 L1/L2/L3가 섞여 있었다. 보안 분류와 혼동하지 않도록 향후 공간 표현은 별도 명칭/필드로 바꿔야 한다. 최신 생성 코드는 이미 공간 생성을 제거했다.

보안은 회사(tenant) 경계 + 사용자별 문서 접근 권한을 함께 확인한다. 단순 level 비교만으로 다른 회사 자료가 열리면 안 된다. 검색·그래프·원문·다운로드·캐시·로그 전부 적용 대상이다. 로그인 목업은 실제 보안 구현이 아니다.

회사 공통 자료(실적·인력·인증·내부 단가)와 공고별 자료(인력 배치안·원가표·투찰 전략)를 구분한다.
**같은 가상 기업 몇 곳이 여러 공고를 검토**하는 구조가 최종 방향이다. 공고마다 기업을 새로 만드는 것은 최신 방향과 다르다.

## 2. 현재 범위와 사용자 의사결정

- UI에는 용역/공사/물품 선택을 제공할 방향. 실제 구현·평가는 용역의 특정 세부 분야를 깊게 진행할 계획이다.
- IT 구축·운영 용역은 후보일 뿐, 실제 문서 완성도 확인 전 확정하지 않았다.
- 13만 건은 수집 규모 추정이다. 공고마다 질문·정답을 만들 필요는 없다.
- 검색용 공고 최대 1만 건, 상세 공고 30~50건, 가상 기업 3~5곳, 검수 질문 200~300개는 논의용 초기 규모이며 확정된 성능 기준이 아니다.
- 공사/물품에서 미구현 기능은 준비 중으로 표시하고, 구현된 것처럼 시연하지 않는다.
- L2/L3는 당분간 합성 기업 자료. 실제 기업 내부 사실인 것처럼 표시하지 않는다.
- 최종 발표일 10월 2일. 현재까지 UI는 풍부한 목업이나 실데이터·권한·모델 연결이 주요 남은 일이다.

## 3. 서비스 동작과 평가 데이터의 차이

사용자 질문 → 권한에 맞는 문서 검색 → Gemma 등의 LLM 답변 생성 → 학습된 탐지 모델로 환각 의심 구간 표시 → 원문 대조.

- 원본 BGE-M3: 검색용 임베딩 모델.
- Gemma: 답변 생성 모델.
- 파인튜닝한 BGE-M3 또는 KLUE: 문서에 비추어 답변 토큰의 환각 가능성을 판단하는 탐지 모델.
- 탐지 모델은 세상의 모든 사실을 아는 모델이 아니다. 입력 문맥에 대한 지지 여부를 판단하며 근거 조항을 자동으로 정확히 찾아준다고 보장할 수 없다.
- 실적/수치/기간 비교의 명시적 규칙 검증과 학습된 환각 탐지는 구분해야 한다.

질문·정답셋은 서비스 동작의 사전 요건이 아니라 평가용이다. 먼저 일부 질문으로 실제 답변을 생성하고 사람이 원문과 대조해 환각 구간을 표시할 수 있다.
모델 생성 답변은 검수 전에는 정답이 아니다. 기준 정답·근거와 실제 생성 답변을 분리한다. 보안 접근 차단 평가는 환각 평가와 별도다.
13만 건 전량 생성은 불필요할 수 있다. 필요하면 100건 파일럿으로 토큰·시간·품질 측정 후 확대한다. 구독 20x는 무제한 API 대량 생성 보장이 아니다. 가격/정책은 당시 공식 문서를 재확인한다.

**실제 샘플을 받은 뒤 폴더 정리/manifest 변환 어댑터를 작성하기로 했다. 아직 미구현이다.**

## 5. 최신 procurement-pipeline 코드

로컬 프로젝트 루트: `C:/Users/aidan/OneDrive/바탕 화면/AI프로젝트`
패키지: `procurement-pipeline/` — Python 3.10+, 표준 라이브러리만 사용.

| 파일 | 역할 |
|---|---|
| common.py | JSONL/CSV 입력, JSON 저장, 해시 |
| prepare.py | manifest 검사, SQLite 집계, 섹터 추천, 대표 공고·근거 청킹 |
| generate.py | Chat Completions 호환 요청 준비/실행, 제한된 병렬 처리·재시도·결과 재사용 |
| security_schema.py | 최신 L2/L3 합성 프롬프트·검증·출력 스키마 |
| test_pipeline.py | 로컬 테스트 3개 |
| make_example.py | 가상 8건 테스트 입력 생성 |
| README.md | 입력 계약·실행법·한계 |

입력 manifest는 공고 ID+version별 행이며 attachments에 파일 경로·파서 결과 경로·성공 상태·integrity_ok가 필요하다.
원천 PDF/HWP 파싱/OCR은 포함하지 않는다. 기존 파서가 page/section/text JSONL을 제공해야 한다.
실제 파일 존재와 크기, 다운로드/파싱 성공, integrity_ok를 확인한다. 내용의 완전성까지 보장하지 않는다.
중복은 공고 내부 해시/경로 기준. 같은 ID+버전의 내용 충돌은 중단한다. 정정공고 최신 선택은 상위 전처리에서 해야 한다.

추천 점수: 핵심 3종 확보 비율 Wilson 하한 80% + 사용 가능 첨부 비율 20%.
핵심 그룹: 입찰공고 / 제안요청(RFP) / 과업·규격. 소규모 분야 과대평가를 줄이기 위해 최소 모수와 완전 공고 수를 요구한다. 미달이면 추천 보류.
대표 표본은 월·기관·예산 규모별 순환 추출로 시연 다양성을 추구한다. 무작위 모집단 평가 표본은 아니다.
공고당 최대 본문 1만 자, 키워드 우선/문서별 순환 선택. 전체 문서를 LLM에 보내지 않는다.

generate.py는 기본적으로 요청 파일만 만들며 네트워크 호출이 없다. --execute를 명시해야 전송한다.
기본 40건, workers=1, retries=2, 입력 바이트·출력 토큰 상한. 바이트는 정확한 토큰 추정이 아니다.
LLM_API_KEY는 환경변수. 서버 설치/실행은 미포함. 실제 LLM 호출은 아직 하지 않았다.
성공 결과는 schema_version=2, public_notice(L1), company, records(L2/L3), scenario_reference를 가진다.
인용 문자열 일치만 검사한다. L1 인용은 합성 기업 실적/원가의 진실성을 입증하는 근거가 아니다.

2. 실제 문서 현황으로 메인 용역 세부 분야 결정. 미확보 숫자를 추측하지 않기.
3. 가상 기업 마스터 중심으로 합성 스키마 변경. L2/L3 보안 분류 유지.
4. 검수 가능한 소규모 시나리오부터 실행하고 표본 확대.
5. UI 목업 → 실제 RAG/탐지/권한 연결을 구분해 구현.

사용자 선호: 자연스러운 한국어, 쉬운 용어. 실행 요청이면 구체적 파일/복붙 명령 제공. 팀원 지시는 담당·분량·제출물·기한까지. 반복 확인 질문 최소화. 완료/미완료를 정확히 구분하기.
