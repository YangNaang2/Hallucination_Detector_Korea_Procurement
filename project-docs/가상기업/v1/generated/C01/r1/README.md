# 한빛IT L2·L3 문서 시범 생성 결과

회사 C01 / tenant `astra-c01` / 회사 상태 기준일 2026-04-01 / 원장 1.0.0 / 문서 1.0.0-r1.

**회사 공통 문서 5개, 청크 27개를 생성하고 기존 질문 5개의 근거를 연결했다.** 원장 사실은 변경하지 않았다. 문서들은 합성 자료 기반 내부 대장이고 실제 발급 증명서가 아니다. `missing` 증빙은 미확보 상태로 남아 있다.

## 생성 문서

각 문서는 동일한 이름의 Markdown·JSON·청크 JSONL 세 형식으로 제공된다. 세 파일을 서로 다른 문서 세 건으로 세지 않는다.

| L2 | [기업·본점·등록 현황](L2/C01-PROFILE-1.0.0-r1.md) | 3 | 기업 현황 / 등록 1개 / 명시적 미보유 1개 |
| L2 | [실적 대장](L2/C01-PERF-1.0.0-r1.md) | 4 | 실적 1건씩; VAT·계약일·완료 상태·지분·증빙 상태 포함 |

청크는 한 대상을 온전히 담는 방식이며 중첩 없이 330~1,223자다. 실제 길이는 `validation_report.json`에서 확인한다. 상한 5,000자는 무조건 자르는 기준이 아니라 초과 시 생성 중단·검토를 요구하는 한도다. 이 표본은 대상별 블록이 충분히 짧아 금액·유효기간·증빙 상태를 분리할 이유가 없었다. 문자 수는 토큰 수가 아니며 임베딩 모델을 선정한 뒤 tokenizer 한도 검사가 필요하다.

## 정본과 참조 규칙

- 정본 텍스트는 문서 JSON의 `content`다. Markdown 파일은 이 문자열과 UTF-8 바이트까지 동일하다. 파일은 LF로 고정한다.
- `text_start`/`text_end`는 정본 전체의 Unicode code point 위치이며 시작 포함·끝 제외다. UTF-8 바이트 위치나 JavaScript UTF-16 위치로 해석하면 안 된다.
- 문서 내부 청크는 기존 `generated_document.schema.json`을 따른다. 외부 JSONL 행은 회사 ID·원장 버전·검수·색인 상태를 추가한 [chunk_export.schema.json](chunk_export.schema.json)을 따른다.
- 청크 ID는 문서 버전과 원장 참조를 묶어 정한다. 같은 버전에서 내용이 달라지면 생성기가 덮어쓰지 않는다. 변경 검토 후 새 문서 버전·출력 경로를 사용한다.
- 공통 문서 생성 함수는 마스터와 생성 목록만 사용한다. 질문·기대답·공고별 판정은 이 함수에 들어가지 않는다. 공고 원문은 L1이며 회사 실적이 실제라는 증거가 아니다.
- 기준일 잔여 FTE와 제한된 원가 예시는 계산값이다. 실적 총액 등 회사 사실은 합성 설정값, 평가 연결에 있는 공고 구절은 원문 추출값이다.

## 질문 5개 연결

[평가용 근거 연결 JSON](evaluation/qa_document_bindings.json)은 기존 질문·기대답 파일을 참조하며, 원문 근거와 생성 회사 문서 근거를 별도 배열에 보존한다. 기대답을 검색 문서에 복사하지 않았다.

| 질문 | 생성 회사 근거 | 함께 확인할 L1 근거 |
|---|---|---|
| Q001 | 실적 P01: VAT 포함 70,000,000원 | 7천만원 이상이라는 원문 하한 |
| Q002 | 실적 P02: VAT 포함 69,999,999원 | 동일 하한; 금액을 반올림하지 않음 |
| Q003 | 실적 P03: 증빙 상태 missing | 실적 증빙 제출 조항 |
| Q004 | 1468 등록 및 0036 명시적 미보유 | 단독 참여 자격과 분담이행 조항 |
| Q005 | 실적 대장 4건 | 말미 공고일 2025-04-24와 제출 일정 2026-05-15 표기 확인 |

이 결과는 ID·인용·문자 위치로 근거가 연결됐다는 뜻이다. 벡터 검색 Recall, LLM 정답률, 환각 탐지 성능을 측정한 것이 아니다. 실제 생성 답변과 span은 null이다.

## 공고별 계획의 차단 상태

[검토 초안](review/scenario_review.md)과 [기계용 검토 기록](review/scenario_review.json)은 L3 설계 검토 자료이며 검색 입력에서 제외했다.

- 현재 SC-WB-C01은 단독 참여 모드이고 회사는 0036을 보유하지 않는다. 실행 가능한 입찰안으로 승인하지 않았다.
- 공고의 기준 연도가 불명확하므로 최근 3년 실적 건수·점수를 확정하지 않았다. 앞 단계에서 보류한 원문 문제를 임의로 해결하지 않았다.
- P03의 2026-06-01~12-17, 0.5 FTE는 기존 합성 초안이다. 실제 착수일이나 발주기관 필수 투입량이 아니다. 기존 배치와 이 독립 초안의 합은 용량 내임을 검사했다.
- 원장 인건비를 적용하면 **온전한 1개월의 직접 인건비 예시**는 `4,130,000 × 0.5 × 1.18 = 2,436,700원(VAT 제외)`이다. 전체 기간 공수·외부 견적·기타 비용은 미확정이므로 전체 원가·투찰가는 null이다.

이 초안은 검색 가능한 배치안·원가표로 승격하지 않았다. 신규 발급 증명서, 협력사 견적, 투찰전략 문서를 꾸며내지 않았다.

## 상태·권한과 실제 색인 전 조건

[manifest.json](manifest.json)은 실제 생성 이력이다. 상위 `document_inventory.json`은 원래 설계 템플릿 목록으로 보존했으며, 증빙 확보 사실을 바꾸지 않았다.

| 단계 | 상태 |
|---|---|
| 문서 생성 / 청크 생성 | 완료 |
| 자동 검사 / 에이전트 내용 검토 | 완료; [검수 기록](review/test_results.json) |
| 사람 검수 승인 | pending — 사람 승인으로 대체 기록하지 않음 |
| 실제 DB 색인 / 서비스 권한 구현 | not_indexed / 이번 작업 범위 밖 |

`rag_ingest=false`를 유지한다. 회사 전체 원장, 이 README, 평가 파일, 검토 기록을 재귀적으로 색인하면 안 된다. 향후 승인된 경우에도 manifest의 `retrieval_input_allowlist`에 있는 회사별 청크 파일만 후보로 삼고 문서 승인·버전·해시를 다시 확인한다. 최종 서비스에서는 로그인 세션의 tenant·활성 소속·역할로 검색 전에 필터링해야 한다.

L2는 자기 회사 bid_analyst/cost_analyst/bid_approver, 이 L3 원가 문서는 자기 회사 cost_analyst/bid_approver에게 허용하는 규칙이다. 타 회사·미로그인·비활성 소속은 차단한다. [권한 검사](review/access_checks.json)는 7개 사용자 상황 × 27개 청크 = **189개 메타데이터 규칙 검사**이며 실서비스 보안 검증이 아니다.

## 검증과 재현

신규 문서 테스트 24개와 기존 마스터 테스트 32개, 합계 **56개가 통과**했다. 금액·VAT, 날짜·인증, 증빙 부족 보존, 중복 배치, 참조·버전·청크 offset, 다른 회사 참조, L2의 L3 혼입, 기대답 필드 및 본문 오염을 검사했다. 생성 파일 전체의 재현 결과를 비교하므로 변조된 JSONL도 거부한다.

자동 검사는 정형 원장의 정확한 투영과 정해진 계산을 검사한다. 에이전트가 Markdown 5종을 읽고 금액 경계, 증빙 상태, 미완료 실적, 인력 잔여량, 인증 기간, L3 VAT 맥락을 확인했다. 키워드 검사만으로 자유서술 자료의 무환각이나 의미상 누출 방지를 보장하지 않는다.

저장소 루트:

```powershell
python procurement-pipeline/generate_c01_documents.py --check
```

새 경로에 재생성할 때:

```powershell
python procurement-pipeline/generate_c01_documents.py --out <검토용_출력경로>
cd procurement-pipeline
python -m unittest -v test_c01_documents.py test_company_master.py
```

외부 Python 패키지·외부 LLM·DB는 필요 없다. 기존 `prepare.py`의 고정 문자 창은 실적·인력 경계를 자를 수 있어 이 합성 대장에는 사용하지 않았다. 기존 공고별 기업 생성기 `generate.py`도 실행하지 않았다.

## 나머지 회사로 확대할 때

회사별 투영·독립 문서·청크·검증 방식은 확대 가능하다. 이번 실행기는 C01 전용이므로 단순히 회사 이름만 바꿔 실행하지 말고 company_id 선택, 원장 위치, 템플릿, 서비스 인증의 보유 주체, 증빙 목록을 함께 일반화해야 한다. 회사별 생성 이력과 승인·적재 상태도 독립 관리한다.

C02의 만료 인증, C03의 부족 증빙, C04의 서비스 CSAP 미확보, C05의 특화 등록은 그대로 보존한다. 각 회사에서 짧은 근거 연결 테스트를 먼저 통과시킨 뒤 확대한다. 실제 임베딩·검색·권한 서버·모델 답변·span 검수는 다음 단계다.
