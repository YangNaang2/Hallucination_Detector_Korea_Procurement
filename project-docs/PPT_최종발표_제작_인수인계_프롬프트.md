## 3. 프로젝트를 다음과 같이 이해해라

ASTRA는 나라장터 공고와 합성 기업 자료를 보안등급별로 구조화하고, 사용자 권한에 맞는 근거만 검색해 로컬 LLM 답변을 생성한 뒤, 규칙 검사와 학습된 환각 탐지 모델로 답변을 다시 확인하는 의사결정 지원 시스템이다.

핵심 흐름:

1. 나라장터 OpenAPI에서 4·5·6월 공고와 첨부문서를 수집
2. 원본 파일을 보존하고 텍스트 파싱 및 JSONL·manifest 구조 생성
3. 변환·정제 및 문서 완전성 분석 후 정보시스템 분야 표본 51건 선정
4. 팀원 5명이 공고문·제안요청서·과업지시서 등에서 참가자격, 실적, 인력, 인증, 지역, 일정, 예산, 공동수급 조건을 추출
5. 조건 분포를 바탕으로 강점과 제약이 다른 가상 기업 5곳 설계
6. 실제 공개 공고는 L1, 가상 기업 내부 실적·인력·인증 자료는 L2, 합성 원가·마진·투찰 검토 자료는 L3로 구성
7. 문서를 의미 단위로 청킹하고 문서 ID, 공고번호, 회사, tenant, 보안등급, 역할, 버전 등 메타데이터 부여
8. 사용자 질문 전에 공고·회사·tenant·역할·보안등급·시나리오로 검색 후보 제한
9. 키워드 검색과 벡터 검색을 결합해 근거 청크 선정
10. 선택한 근거와 질문을 로컬 LLM에 전달해 답변과 인용 생성
11. 금액·VAT·기간·인증·FTE 등의 규칙 검사와 환각 탐지 모델로 생성 답변 재검토
12. UI에서 답변, 출처, 관련 근거, 환각 의심 구절, 조건별 충족·미충족·자료부족 상태 표시

## 4. 반드시 유지할 사실 구분

### L1

- 나라장터에서 수집한 실제 공개 공고와 공개 첨부문서
- 공고문, 제안요청서, 과업지시서, 규격서, 시방서 등의 공개 조건

### L2

- 51건 공고 조건을 비교할 수 있도록 만든 가상 기업 5곳의 합성 내부 자료
- 회사 기본정보, 업종·등록, 실적, 인력, 자격, 인증, 증빙 상태와 배치 가능량
- 실제 기업에서 받은 기밀자료가 아님

### L3

- 가상 기업의 합성 민감 자료
- 인건비, 원가, 비용 가정, 마진 정책, 공고별 원가표와 투찰 검토
- 실제 업체 견적이나 실제 투찰 전략이 아님

### 권한 필터

- L1·L2·L3로 문서를 분류하는 것과 권한 필터는 구분한다.
- 보안등급은 문서의 성격을 나타낸다.
- 권한 필터는 신뢰된 서버 세션의 회사·tenant·역할을 이용해 검색 전에 허용 문서만 후보로 남기는 과정이다.
- 브라우저에서 역할 이름을 바꾸는 것만으로 접근 권한이 확장된다고 설명하지 마라.

### 검색

- 키워드 검색은 공고번호, 업종코드, 금액, 날짜, 정확한 용어 검색에 유리하다.
- 벡터 검색은 표현이 달라도 의미가 유사한 문맥 검색에 유리하다.
- 현재 파일럿은 두 검색 결과를 결합하는 권한형 하이브리드 RAG다.
- 별도 그래프 DB를 통한 다단계 경로 추론이 완성된 GraphRAG라고 설명하지 마라.

### 300개 Q-A-R

- 300개 질문·기대답·근거는 RAG 검색 코퍼스가 아니다.
- 실제 입찰 담당자가 물을 법한 질문을 미리 구성한 평가 데이터셋이다.
- RAG 검색, 생성 답변, 환각 탐지 성능을 평가하는 기준으로 사용한다.
- 현재 기록에는 생성 답변 295건과 정상 접근 차단 5건이 있다. 최신 결과 파일로 다시 확인해라.
- 25문항에는 팀원 사람 검수와 통합 조정안이 있으나 최종 사람 승인 상태는 별도로 확인해야 한다.

### 현재 확인된 파일럿 수치

다음 수치는 최신 manifest와 실제 파일을 다시 확인한 경우에만 사용한다.

- 표본 공고 51건
- 가상 기업 5곳
- 평가 질문·기대답·근거 300건
- RAG 파일럿 코퍼스 223개 문서, 3,275개 청크
  - L1 167개 문서, 3,002개 청크
  - L2 34개 문서, 159개 청크
  - L3 22개 문서, 114개 청크
- 별도 추적된 읽을 수 없는 첨부 16개

나라장터 전체 수집 건수와 월·업무별 통계는 `3개월_통합현황.md`와 실제 집계 파일을 기준으로 표기한다. 발표 편의를 위해 `13만 건`과 같은 반올림 수치를 사용할 때에는 `약`을 붙이고, 정확한 수치와 혼용하지 마라.

## 5. 환각 탐지 현황

환각 탐지 후보는 KLUE, XLM-R, BGE-M3 기반 토큰 분류 체크포인트다. 검색 임베딩 모델과 환각 탐지용 BGE-M3 체크포인트를 구분한다.

목표 흐름:

`질문 → 권한형 RAG 검색 → 로컬 LLM 답변 → 실제 입력 근거와 답변 결합 → 토큰 분류 → 의심 구절의 Unicode 문자 위치 변환 → UI 형광펜 표시`

실제 300문항 평가가 진행 중이면 완료된 결과 범위만 사용한다. 다음을 성능 완료로 표현하지 마라.

- 체크포인트가 존재한다는 사실
- 대시보드에 모델 연결부가 있다는 사실
- 25문항 사람 검수 자료가 있다는 사실
- 소수 예제에서 추론이 실행됐다는 사실

모델 성능 슬라이드에는 최소한 데이터 범위, 사람 정답지 상태, 평가 기준일, threshold, 긴 답변 잘림 처리, Precision·Recall·Span F1을 함께 적어라. 결과가 미완료면 표와 차트의 자리만 설계하고 `평가 진행 중`이라고 표시해라.

   - 나라장터와 환각 탐지를 함께 다루는 이유가 제목에서 드러나게 구성
2. 문제 상황
   - 공고 조건·전산 제출·정정공고·평가 기준 불명확 사례 중 검증된 사례 2~3개
   - 외부 LLM 기밀 유출과 근거 없는 답변 위험을 짧게 연결
3. 기존 방식의 한계
   - 단순 키워드 검색, LLM 요약, 보안 통제가 분리된 문제
   - 확인되지 않은 비교 수치를 만들지 마라.

### Chapter 2. 해결책 공개

4. 프로젝트 목표
   - 권한에 맞는 근거 검색과 생성 답변 검증을 하나의 흐름으로 제공
5. 전체 파이프라인
   - Input, Process, Output 구조
   - 이후 기술 슬라이드가 이 구조도의 어느 구간인지 반복 표시
6. 사용자 시나리오
   - 공고 선택 → 질문 → 권한 확인 → 검색 → 생성 → 규칙·환각 검증 → 결과 확인

### Chapter 3. 데이터 기반

7. 수집과 표본화
   - OpenAPI, raw, parsed, JSONL의 역할
   - 4·5·6월 수집과 표본 51건 선정 과정
8. L1·L2·L3
   - 실제 공개 공고와 합성 기업 자료의 파생 관계
   - 같은 `가격`도 공개 예산, 회사 실적액, 내부 원가에 따라 등급이 달라지는 예시
9. 평가 데이터
   - 요건추출시트에서 300개 Q-A-R이 만들어진 과정
   - 300개가 RAG 코퍼스가 아니라 평가 기준이라는 점을 명시

### Chapter 4. RAG 엔진

10. 권한 필터
    - viewer, bid_analyst, cost_analyst, bid_approver의 접근 범위
    - 실제 운영 인증 시스템과 파일럿 권한 검증을 구분
11. 하이브리드 검색
    - 키워드와 벡터 검색의 역할
    - 순위 결합과 상위 근거 선정
12. 근거 기반 생성
    - 실제 LLM 입력 형식과 답변·인용 생성
    - 저장 결과, 테스트 응답, 실제 모델 생성을 구분

### Chapter 5. 환각 검증

13. 탐지 구조
    - 생성 답변과 실제 입력 근거를 직접 비교하는 토큰 분류
    - 문장 O/X보다 구절 단위 형광펜 표시

    - 모델 크기나 체크포인트 존재만으로 성능 우열을 주장하지 마라.
15. 오류 사례
    - 놓친 환각 구절, 정상 구절 오탐, 잘린 답변, 잘못된 인용번호 등 대표 사례

    - 저장 결과 모드와 실제 모델 모드를 명확히 표시
18. 성과와 한계
    - 실제 구현 완료, 현재 미연결, 추가 검증 필요 항목을 구분
    - 다음 단계는 운영 인증, L2·L3 자유 질문, 전체 300문항 탐지 평가, Live DB 연결 중심

## 7. 수상작에서 가져올 발표 문법

사용자가 제공한 수상작의 장점은 내용이나 브랜드를 복제하는 것이 아니라 다음 전개 방식이다.

- 강한 표지와 짧은 목차
- 새로운 장이 시작될 때 짧은 섹션 표지 사용
- 전체 시스템 구조를 먼저 공개
- 이후 슬라이드마다 전체 구조도의 현재 구간을 작은 미니맵으로 표시
- 한 기술 슬라이드 안에서 입력, 핵심 처리, 출력이 보이게 구성
- 기술 설명 뒤에는 데이터셋, 평가 결과, 오류 사례 배치
- 후반부에 실제 데모와 사용자 관점 효과 배치
- 마지막에 한계와 확장 방향을 숨기지 않고 제시

Netflix·POFLIX 로고, 사용자 인터페이스, 고유 브랜드 표현은 복제하지 마라. ASTRA의 독립적인 시각 언어로 재해석해라.

## 8. 권장 디자인

- 16:9 와이드
- 어두운 네이비 또는 블랙 기반의 시네마틱 테크 스타일
- ASTRA 강조색은 청록, 파랑, 제한적인 코럴 또는 오렌지
- 섹션마다 진행선을 유지해 현재 위치를 보여준다.
- 슬라이드 상단 제목, 중앙 핵심 시각자료, 하단 한 문장 결론의 구조를 일관되게 사용한다.
- 텍스트보다 실제 다이어그램, 검증된 차트, 대시보드 화면을 우선한다.
- 카드가 지나치게 많아 대시보드처럼 보이지 않게 한다.
- 본문 글자는 발표 화면에서 읽을 수 있는 크기로 유지한다.
- 슬라이드마다 핵심 메시지는 하나만 둔다.
- 표·차트에는 단위, 표본 수, 기준일과 출처를 표시한다.

시각자료가 필요하면 저장소의 SVG와 실제 대시보드 스크린샷을 우선 사용한다. 장식용 이미지를 넣을 경우 발표 내용과 직접 관련된 이미지만 사용하고 출처를 기록한다.

## 9. 절대 하면 안 되는 표현

- `300개 질문이 RAG다`
- `L2·L3는 실제 기업의 기밀자료다`
- `모든 공고 첨부가 완전히 파싱됐다`
- `AI가 전체 입찰 적격 여부를 자동 확정한다`
- `탐지 구절이 0개이므로 답변이 정확하다`
- `25문항 검수로 300문항 성능을 증명했다`
- `자동 검증 통과가 사람 승인 완료를 의미한다`
- `그래프 UI가 있으므로 완성형 GraphRAG다`
- `저장 결과 재생을 실제 실시간 모델 생성이라고 표현한다`
- 출처 없이 환각률, 정확도, 처리시간, FPS 등의 숫자를 만든다.

개별 조건 충족을 전체 입찰 적격 판정으로 확대하지 마라. 자료가 없거나 원문이 충돌하면 `자료부족`, `원문충돌`, `추가 확인 필요`로 표시한다.

## 11. 검증
