# 환각 판별 프로젝트 — 우리가 만들 것

> **한 줄: 거대한 AI가 지어낸 말을, 100배 작은 AI가 잡아낸다.**

이 문서는 팀 전체가 읽는 문서다. 프로젝트가 무엇인지, 어떤 파트로 나뉘는지, 각자 무엇을 언제 하는지를 담았다.

---

## 1. 무슨 문제를 푸나

**사용자** — "저 만 40세인데 청년창업 지원사업 신청할 수 있나요?"

**챗봇** — "만 39세 이하 청년이면 신청할 수 있습니다. **지원금은 최대 1억 원**까지 받으실 수 있습니다."

여기서 **"1억 원"은 챗봇이 지어낸 말**이다. 공고문에는 **5천만 원**이라고 적혀 있다.

사용자는 이걸 알아챌 방법이 없다. 문장이 자연스러우니까. 그대로 믿고 사업계획서를 쓴다.

**우리가 만드는 것 = 답변의 문장마다 공고문과 대조해 형광펜을 그어주는 시스템.**

| 답변 문장 | 결과 |
|---|---|
| 만 39세 이하 청년이면 신청할 수 있습니다 | 🟩 **초록** · 공고문에 있음 |
| 예비창업자도 대상에 포함됩니다 | 🟨 **노랑** · 공고문에 언급 없음 |
| 지원금은 최대 <ins>1억 원</ins>까지 받을 수 있습니다 | 🟥 **빨강** · "1억 원"만 밑줄 |

---

## 2. 왜 어려운가 (= 왜 프로젝트가 되는가)

> "그냥 문자열 비교하면 되는 거 아냐?"

안 된다. 아래 세 가지 때문이고, **이 셋을 다루는 게 프로젝트 내용의 전부**다.

**① 같은 뜻인데 글자가 다르다**
공고문은 "공고일 기준 **만 39세 이하인 자**", 챗봇은 "**만 39세 이하 청년이면**".
글자는 다른데 뜻은 같다 → 의미를 이해하는 모델이 필요하다.

**② "근거가 없는 것"과 "근거와 반대인 것"은 다르다**
- **예비창업자** → 공고문에 언급 자체가 없음 = **모르겠다**
- **1억 원** → 공고문에 5천만 원이라 적혀 있음 = **틀렸다**

구분을 못 하면, 검색이 실패했을 뿐인데 전부 "거짓말"로 찍어버린다.
**그래서 판정이 2개가 아니라 3개다.**

**③ 문장 전체가 아니라 일부만 틀린다**
"만 39세 이하면 되고, 지원금은 1억 원입니다" → **앞은 맞고 뒤만 틀렸다.**
통째로 빨간칠하면 어디를 고칠지 모른다. **"1억 원" 네 글자만 짚어야 쓸모가 있다.**

## 3. 시스템이 도는 길과 파트 나누기

질문 하나가 들어와서 화면에 뜰 때까지의 순서다. 오른쪽이 담당 파트다.

```
사용자 질문
   ↓
① 검색        공고문 더미에서 관련 조각 3~5개를 찾아온다     ← A 문서·RAG
   ↓
② 답변 생성   LLM이 그 조각을 보고 답변을 쓴다              ← A 문서·RAG
   ↓
③ 문장 쪼개기  답변을 문장 단위로 자른다                     ← C 검증 모델
   ↓
④ 판정        각 문장을 ①의 조각과 대조 → 3분류 + 구간      ← C 검증 모델 ★본체
   ↓
⑤ 표시        초록/노랑/빨강, 클릭하면 근거가 열린다         ← E 프론트
```

### 파트별로 하는 일

| | 파트 | 하는 일 | 끝났다는 기준 |
|:--:|---|---|---|
| **A** | 문서 · RAG | 공고문 수집 → HWP/PDF 파싱 → 항목 단위로 조각내기 → 검색(벡터+키워드) → LLM으로 답변 생성 | 질문을 넣으면 근거와 답변이 JSON으로 나옴 |
| **B** | 학습 데이터 | 공개 데이터 확보 + 로컬 LLM으로 **한국어 환각을 일부러 만들어** 구간 라벨 붙이기 + 라벨링 규칙서 | 한국어 평가셋 확보, 라벨 오염률 보고 |
| **C** | 검증 모델 | 문장을 근거와 대조해 **지지/반박/정보부족 3분류 + 틀린 구간 지목**하는 모델을 직접 학습 | self-check 대비 성능 우위 + 크기별 성능-비용 곡선 |
| **D** | 평가 설계 | 베이스라인 비교, 지표 정의(F1·구간 IoU·신뢰도 보정), 임계값 근거 만들기 | 모든 실험이 같은 표에 들어오는 평가 스크립트 |
| **E** | 프론트 · 진행 | 형광펜 화면, 클릭 시 근거 하이라이트, 데모 시나리오, 일정·발표 | 심사위원이 즉석 질문해도 도는 화면 |

**C 파트가 실제로 만드는 것은 이렇게 생겼다.**

```
입력  →  근거 한 덩어리  +  검사할 문장 하나
출력  →  지지 / 반박 / 정보부족   (반박이면 + 틀린 구간)
```

| 근거 | 검사할 문장 | 출력 |
|---|---|---|
| 신청자격 : 공고일 기준 만 39세 이하인 자 | 만 39세 이하 청년이면 신청할 수 있습니다 | **지지** |
| 지원금 : 사업화자금 최대 5천만 원 | 지원금은 최대 1억 원까지 받을 수 있습니다 | **반박** · 구간 = "1억 원" |
| 신청자격 : 공고일 기준 만 39세 이하인 자 | 예비창업자도 대상에 포함됩니다 | **정보부족** |

## 4. 왜 하필 "작은 모델"인가 — 프로젝트의 주장

④번 판정은 GPT한테 시켜도 된다. "이 문장 근거에 맞아?"라고 물으면 되니까.

**문제는 비용이다.** 답변 하나에 문장이 5개면 GPT를 5번 부른다. 100명이 쓰면 500번. 느리고 비싸서 실시간으로 못 쓴다.

그래서 **④번만 하는 작은 모델을 직접 학습시킨다.** GPT-4보다 1000배쯤 작은데, 이 한 가지 일만큼은 비슷하거나 더 잘한다.

발표에서 보여줄 그래프가 이거다 — **모델 크기 ↔ 정확도 ↔ 속도.**
"이 크기부터는 더 키워도 안 좋아진다"는 지점을 짚고, 그래서 이 크기를 골랐다고 말한다. 감이 아니라 실험으로 정한 게 된다.

실습실 워크스테이션(A5000 24GB) 6대를 여기에 쓴다. 한 대에 한 크기씩 걸면 하루면 곡선이 나온다.

## 5. 데이터는 어디서 오나

**데이터가 세 종류**라서 헷갈리기 쉽다. 성격도, 구하는 방법도, 담당도 다르다.

| | 무엇 | 어디서 | 담당 | 언제 |
|---|---|---|---|:--:|
| **①** 학습용 | 모델을 가르칠 정답 데이터 | **Hugging Face에서 코드 3줄로 다운로드** | C | 0주차 |
| **②** 근거 문서 | 실제 서비스에서 대조할 공고문 | 기업마당 · K-Startup 공개 공고 | A | 1~2주차 |
| **③** 한국어 환각 | 우리가 직접 만드는 평가·학습 데이터 | 로컬 LLM으로 생성 후 구간 라벨링 | B | 2~4주차 |

### ① 학습용 데이터 — 실제로 불러오는 법

```python
from datasets import load_dataset

# 영어 3분류 (지지 / 반박 / 정보부족)
fever = load_dataset("fever", "v1.0")

# 한국어 NLI (함의 / 중립 / 모순 → 우리 3분류와 거의 대응)
klue   = load_dataset("klue", "nli")
kornli = load_dataset("kor_nli", "multi_nli")
```

알아서 받아서 로컬 캐시에 넣어준다.
**RAGTruth만 예외로 GitHub에서 직접 받는다** — `ParticleMedia/RAGTruth`. RAG 상황의 환각을 **구간 단위로** 라벨링한 데이터라 이 프로젝트에 가장 잘 맞는다.
(데이터셋 ID는 가끔 바뀌므로 Hugging Face 페이지에서 한 번 확인할 것.)

> **데이터를 구하는 게 일이 아니라, 받아놓고 실제로 어떻게 생겼는지 확인하는 것이 일이다.**
> 특히 RAGTruth의 구간 라벨 형식을 A·B·C가 함께 봐야 한다. B가 만들 한국어 데이터를 그 형식에 맞춰야 하기 때문이다.

### ③ 한국어 환각 데이터는 이렇게 만든다

실습실 워크스테이션에 오픈소스 LLM을 띄우고, 공고문을 근거로 주면서 답변을 대량으로 만든다.
이때 **일부러 환각을 유도한다** — 온도를 높이거나 근거를 일부만 준다.
근거 문서가 우리 손에 있으니 어디가 틀렸는지 표시할 수 있다.

## 6. 1주차에 팀이 함께 정할 것 — JSON 계약

**이 프로젝트에서 전원이 모여야 하는 유일한 지점이다.** 주고받을 데이터의 모양을 먼저 정해야 각자 병렬로 일할 수 있다.

```json
{
  "question": "만 40세인데 청년창업 지원사업 신청할 수 있나요?",
  "answer":   "만 39세 이하 청년이면 신청할 수 있습니다. 지원금은 최대 1억 원입니다.",
  "evidence": [
    { "chunk_id": "2026_youth_startup#3",
      "text": "신청자격 : 공고일 기준 만 39세 이하인 자 ..." }
  ],
  "claims": [
    { "claim_id": 1,
      "text":       "만 39세 이하 청년이면 신청할 수 있습니다.",
      "char_span":  [0, 24],
      "verdict":    "SUPPORTED",
      "confidence": 0.94,
      "cited":      { "chunk_id": "2026_youth_startup#3", "char_span": [0, 28] },
      "error_span": null },

    { "claim_id": 2,
      "text":       "지원금은 최대 1억 원입니다.",
      "char_span":  [25, 42],
      "verdict":    "REFUTED",
      "confidence": 0.88,
      "cited":      { "chunk_id": "2026_youth_startup#7", "char_span": [12, 34] },
      "error_span": [33, 37] }
  ]
}
```

A가 위쪽(question · answer · evidence)을 채우고, C가 아래쪽(claims)을 채우고, E가 그걸 읽어서 화면에 그린다.

**이것만 정해두면 각자 가짜 데이터로 자기 파트를 끝까지 만들 수 있다.**
E는 손으로 쓴 JSON으로 형광펜 화면을 완성하고, C는 A가 없어도 영어 데이터로 모델을 돌린다. 3주차에 진짜 데이터를 흘려보내면 그대로 붙는다.

## 7. 5주 일정

| 주차 | A 문서·RAG | B 데이터 | C 검증 모델 | D 평가 | E 프론트 |
|:--:|---|---|---|---|---|
| **1** | 공고 수집·파싱 | 라벨링 규칙서 · 공개 데이터 | **베이스라인** · 공개 데이터 확인 | 지표 확정 | 목업 JSON으로 UI |
| **2** | 청킹 · 검색 | 한국어 환각 생성 시작 | 판정기 v1 (영어) | 평가 스크립트 | UI 계속 |
| **3** | LLM 서빙 · 연결 | 구간 라벨링 | 한국어 + 구간 지목 | 평가 스크립트 | 실데이터 연결 |
| **4** | 튜닝 | 재검수 · 오염률 | **크기 실험 · 제거 실험** | 임계값 역산 · 결과표 | 화면 마감 |
| **5** | 통합 | — | 통합 | 최종 결과표 | 시연 리허설 |

**1주차 끝에 JSON 계약을 확정하는 것이 유일한 필수 동기화 지점이다.** 그 이후 3주차까지는 각자 자기 것만 만든다.

## 8. 이번 주에 각자 앉아서 할 일

| 파트 | 할 일 |
|:--:|---|
| **A** | 기업마당·K-Startup에서 공고문 20~30건 받아 HWP/PDF 파싱이 되는지부터 확인 |
| **B** | RAGTruth 구간 라벨 형식 확인 → **라벨링 규칙서 초안** 작성 (특히 "의견·평가 문장은 검증 대상이 아니다"의 경계를 예시로) |
| **C** | ① RAGTruth 열어보기 (반나절) ② **GPT로 self-check 만들어 점수 재기** (하루) ③ DeBERTa로 FEVER 학습해 첫 숫자 (2~3일) |
| **D** | 어떤 숫자로 성공을 판정할지 확정 — 문장 F1, 구간 IoU, "정보부족" 재현율 |
| **E** | 위 JSON을 손으로 하나 써서 **형광펜 화면 목업** 만들기 |

### 놓치면 안 되는 것 두 개

**베이스라인을 건너뛰지 말 것.** 기준선 없이 4주를 보내면, 모델이 0.78이 나와도 그게 좋은 건지 나쁜 건지 알 수가 없다. 가장 흔한 실패다.

**전체 정확도만 보지 말 것.** 클래스별로 따로 봐야 한다. 특히 **"정보부족"의 재현율**이 낮으면 시스템이 모르는 걸 아는 척한다는 뜻이다.

## 9. 자주 나오는 질문

**Q. "모델을 학습시킨다"는 게 실제로 뭘 하는 건가?**
`(근거, 문장) → 정답` 쌍 수만 개를 모델에 반복해서 보여주고, 틀릴 때마다 조금씩 고치게 하는 것.
코드는 짧다. `AutoModelForSequenceClassification`에 `num_labels=3`을 주는 게 사실상 전부다.

**Q. 한 줄로 하면 무슨 프로젝트인가?**
**"LLM을 평가하는 LLM"이 아니라 "LLM을 평가하는, LLM이 아닌 것"이다.**
평가 *대상*은 LLM이 맞지만, 평가 *주체*는 LLM이 아니라 작은 분류 모델(BERT 계열)이다.

| | 지금 업계 표준 (RAGAS 등) | 우리 |
|---|---|---|
| 판정하는 것 | GPT-4 같은 **LLM** | 작은 **분류 모델** |
| 하는 일 | 문장을 **생성**해서 답함 | 3개 중 **하나를 고름** + 구간 찍기 |
| 크기 | 수천억 | 1~4억 |
| 비용·속도 | 비싸고 느림 | 싸고 빠름 |
| 지어낼 수 있나 | **있음** | **없음** |

마지막 줄이 결정적이다. 우리 모델은 **문장을 만들 줄 모른다.** 할 수 있는 것이 "셋 중 하나 고르기"와 "몇 번째 글자부터 몇 번째 글자까지 찍기"뿐이라 **구조적으로 환각이 불가능하다.** "검증하는 AI가 거짓말하면?"에 대한 답이 이것이다.

**Q. BERT가 정확히 뭔가?**
**GPT는 쓰는 모델이고, BERT는 읽는 모델이다.**

| | GPT (LLM) | BERT |
|---|---|---|
| 하는 일 | 다음 단어를 예측해 **문장을 만든다** | 문장을 **이해하고 분류한다** |
| 보는 방향 | 왼쪽 → 오른쪽 (앞만 봄) | **양쪽 다 봄** |
| 출력 | 글 | 라벨 / 위치 |
| 크기 | 수천억 | 1~4억 |

이름 자체가 그 뜻이다 — **B**idirectional(양방향) **E**ncoder Representations from Transformers. 구글이 2018년에 발표했다.

학습 방식도 다르다. BERT는 문장에서 단어를 가리고 맞히게 시킨다.
> "만 39세 이하 **[빈칸]**이면 신청할 수 있습니다"

빈칸을 맞히려면 **앞뒤를 다 봐야** 하므로 문장을 통째로 이해하게 된다. GPT는 앞만 보고 다음 단어를 이어붙이는 훈련을 한다.

**우리가 시킬 일은 "이 문장이 근거와 맞나?"**이고, 이는 읽고 판단하는 일이지 글을 쓰는 일이 아니다. 그래서 글을 쓸 필요가 없으니 작아도 되고, 글을 못 쓰니 지어낼 수도 없다.
비유하자면 **GPT는 작가, BERT는 채점자**다. 작가에게 채점을 시켜도 되지만 비싸고 느리며 가끔 자기가 이야기를 지어낸다.

실제로는 BERT 자체보다 개량판을 쓰며, 통칭 "BERT 계열"이라 부른다.

| 모델 | 용도 |
|---|---|
| **DeBERTa-v3** | 영어. BERT 개량판 중 성능이 좋다 |
| **klue/roberta** | 한국어 특화 |
| **mDeBERTa-v3** | 다국어. 영어로 배운 것을 한국어로 옮길 때 |

**Q. 우리만의 평가지표를 만드는 건가?**
아니다. 두 가지를 구분해야 한다.
- **평가지표(metric)** = 성능을 재는 자 → **표준을 쓴다** (F1, 구간 IoU, ECE)
- **평가 모델(judge)** = 실제로 판정하는 것 → **이것을 우리가 만든다**

지표를 직접 만들면 오히려 위험하다. 자기에게 유리한 자를 만들어 자기를 재는 것은 심사에서 "순환 평가"로 감점된다. **남들이 쓰는 표준 자로 재서 이기는 편이 훨씬 강하다.**

다만 우리가 직접 정하는 것도 있다 — **판정 체계**(왜 2분류가 아니라 3분류인지, 왜 문장이 아니라 구간인지), **임계값**(신뢰도 몇 %부터 초록으로 칠할지, 데이터에서 역산), **오답 분류 기준**(검색 실패인지 판정 실패인지).

**Q. 그냥 GPT가 더 좋은 거 아닌가?**
전반적으로는 그렇다. 하지만 **"이 문장이 근거와 맞나"** 이 하나만 놓고 보면 다르다.
작은 모델을 그 일만 시키면 비슷한 정확도를 내면서 훨씬 빠르고 싸다.
**그걸 숫자로 증명하는 것이 이 프로젝트의 결론이다.**

**Q. 검증하는 것도 AI인데, 걔가 거짓말하면?**
심사에서 반드시 나올 질문이다. 답은 이렇다 — 검증 모델이 판정할 때 **근거의 어느 위치를 봤는지 좌표를 같이 출력**하게 하고, 그 좌표의 글자를 원문에서 꺼내 대조한다. 없으면 지어낸 것이므로 즉시 걸린다.

**Q. 그러면 RAG는 안 만드나?**
만든다. **A 파트가 통째로 RAG 구축이다** — 공고문 수집 → 파싱 → 청킹 → 검색 → LLM 답변 생성.

다만 **RAG는 이 프로젝트의 자랑거리가 아니라 무대**다. 두 가지 이유에서다.
- RAG 구축 자체는 이제 튜토리얼 수준이라 심사에서 점수가 되지 않는다. 기성 라이브러리(LangChain·LlamaIndex 등)를 써도 무방하다.
- **RAG가 가끔 틀려줘야 검증 모델이 잡아낼 것이 생긴다.** 여기서 완벽을 추구하면 프로젝트 본체가 할 일이 없어진다.

즉 A 파트의 목표는 **평범하게 · 빠르게 · 튼튼하게**다. "우리가 모델을 만들었다"가 성립하는 지점은 A가 아니라 C다.

**Q. 검증 대상 문서는 무엇으로 하나?**
**아직 확정 전이며 회의에서 정한다.** 다만 팀에 도메인 지식이 있는 사람이 없다는 점을 반영하면 후보가 좁혀진다.

이 프로젝트에 맞는 문서의 조건은 다섯 가지다.

| 조건 | 왜 필요한가 |
|---|---|
| **팀이 내용을 이해할 수 있다** | 라벨이 맞는지 팀이 직접 판단해야 한다. 이해 못 하는 문서로는 평가셋을 못 만든다 |
| **숫자·조건이 많다** | "5천만 원인데 1억이라 했다"처럼 **틀린 것이 명확해야** 지지/반박 판정이 성립한다. 서술형 문서는 판정 자체가 애매해진다 |
| 항목·조항 구조가 뚜렷하다 | 청킹이 쉽고 근거 인용이 명확해진다 |
| 공개돼 있고 파싱이 쉽다 | 확보 속도가 곧 프로젝트 속도다 |
| 틀리면 실제 피해가 있다 | "왜 이걸 검증하는가"에 답이 된다 |

### 후보 비교

| | 후보 | 팀 이해도 | 데이터 확보 | 숫자·조건 | 틀렸을 때 |
|:--:|---|:--:|:--:|:--:|---|
| **1** | **대학 학사요람 · 졸업요건** | ★★★★★ | ★★★★★ | ★★★★★ | 졸업이 미뤄진다 |
| 2 | 채용공고 지원자격 | ★★★★★ | ★★★★ | ★★★★ | 지원 기회를 놓친다 |
| 3 | 정부 지원사업 공고 | ★★★ | ★★★ | ★★★★★ | 금전 손해 |
| — | 법률 (근로기준법 등) | ★ | ★★★★★ | ★★★★ | 법적 불이익 |

**법률은 제외한다.** 조항 구조가 명확해 기술적으로는 좋지만, **법조문은 읽어도 이해가 어려워** 팀이 "이 답변이 맞나"를 판단할 수 없다. 라벨을 만들 수 없으면 프로젝트가 서지 않는다.

**정부 공고문도 약점이 있다.** HWP 파일에 표가 많아 **파싱이 지저분하고 공고마다 형식이 제각각**이다.

### 1순위 : 대학 학사요람

- **팀 전원이 이미 전문가다.** 졸업학점·이수구분·재수강 규정·계절학기 한도는 전부 몸으로 겪은 것이라 라벨을 자신 있게 붙일 수 있다
- **평가셋 만들기가 가장 쉽다.** 질문 50~100개를 팀원들이 자기 경험에서 그냥 쏟아낼 수 있다 ("재수강하면 원점수가 남나요?")
- **문서 집합이 자연스럽게 닫힌다.** "우리 학교 요람 하나"로 범위가 딱 잘린다
- **환각이 잘 난다.** LLM이 일반적인 대학 규정 상식으로 뭉개서 답하는데, 규정은 학교마다 다르다. 우리가 잡을 것이 많아진다
- **심사위원도 즉시 이해한다**

### "의의가 가볍다"는 지적은 이렇게 뒤집는다

데모 마지막에 **문서 집합을 통째로 갈아 끼워서 보여준다.** 학사요람으로 돌던 것이 다른 문서로 그대로 돈다.

그러면 "왜 학사요람이냐"는 질문이 **"우리 방법은 도메인에 상관없이 작동한다"**는 강점으로 바뀐다. 우리가 만든 것은 검증 모델이지 학사요람 챗봇이 아니기 때문이다.
