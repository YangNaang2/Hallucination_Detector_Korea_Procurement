## 슬라이드 1. 추진 배경과 연구 질문

### 화면 본문

**입찰 조건의 대조와 AI 답변의 근거 확인**

- 실무 문제: 공고·정정·회사 증빙을 함께 읽어 참가 조건을 검토
- 공식 사례: 입찰 취소 이의에 대한 권익위 시정권고(2019)
- 연구 질문: 번역 데이터로 학습한 탐지기가 실제 한국어 공고에서도 의심 구절을 찾아낼 수 있는가?

| 접근 | 선행연구·역할 | 이번 프로젝트에서 확인할 지표 |
|---|---|---|
| 키워드·일반 RAG | 관련 문서 검색과 답변 생성 | Recall@K, Hit Rate, 지연 시간 |
| GraphRAG | 관계·커뮤니티를 활용한 전역 질의 요약 | 관계 확장 전후 검색·근거 정확도 |
| LettuceDetect 계열 | 문맥과 답변을 함께 읽는 구간 탐지 | 환각 클래스 P/R/F1, span F1 |
| 우리 적용 | 한국어 탐지 + 숫자 규칙 + 원문·공간 UI | 오류 발견, 오판·보류, 검토 시간 |

**선행연구의 과제와 평가 단위가 달라 성능 숫자를 직접 순위화하지 않는다.**

### 발표 대본

입찰 담당자는 공고를 찾은 뒤에도 참가 자격, 변경된 일정, 회사 실적과 증빙을 대조해야 합니다. 국민권익위원회의 2019년 의결은 공고 입력과 제출 조건을 둘러싼 입찰 취소 분쟁에서 절차 진행을 시정권고한 사례입니다. 문서와 실제 제출 사실을 함께 읽어야 하는 문제를 보여줍니다. 다만 이 사례는 AI 사고나 분쟁 증가율을 입증하는 자료는 아닙니다.

AI로 이 업무를 지원할 때는 별도의 위험이 있습니다. RAGTruth는 검색 문맥을 제공해도 문맥에 없는 내용이나 모순된 답변이 생길 수 있음을 다룹니다. LettuceDetect와 Turk-LettuceDetect는 이를 구간 탐지와 토큰 분류 문제로 접근했습니다. 저희는 이 방법을 한국어로 구현하고 실제 나라장터 문서에서의 적용 가능성을 평가하려고 합니다. GraphRAG 연구는 문서 집합 전체를 요약하는 전역 질의에 초점이 있어, 입찰 조항 판정의 정확도를 그대로 보장하지 않습니다. 공간 화면도 문서를 탐색하는 인터페이스이며, 검토 시간 단축 효과는 별도 사용자 평가가 필요합니다.

### 화면 레이아웃 구성안

템플릿의 좌측 설명·우측 비교표 구성을 사용한다. 왼쪽 약 35%에 실무 문제와 연구 질문, 오른쪽 약 60%에 편집 가능한 접근법 비교표를 둔다. 표 하단에 비교 조건의 한계를 한 줄 표시한다. 검증하지 않은 정확도 막대그래프 대신 평가 대상을 비교한다.

### 출처 및 보충 설명

- [국민권익위원회 공식 의결, 2019-10-07](https://www.acrc.go.kr/board.es?act=view&bid=1010&list_no=27506&mid=a10504010000&nPage=41&tag=): 공고·제출 조건 관련 분쟁의 존재만 뒷받침한다.
- [RAGTruth, ACL 2024](https://aclanthology.org/2024.acl-long.585/): 검색 문맥에도 지지되지 않거나 모순되는 답변 및 구간 라벨 평가.
- [LettuceDetect, 2025](https://arxiv.org/abs/2502.17125), [Turk-LettuceDetect, 2025](https://arxiv.org/abs/2509.17671): 토큰·구간 탐지와 번역 기반 언어 확장.
- [GraphRAG, Edge et al.](https://arxiv.org/abs/2404.16130): 그래프 색인·커뮤니티 요약과 전역 질의 평가. 입찰 판정 정확도·조항 검증 속도의 근거로 전용하지 않는다.
- 공간 맥락의 효용, 검토 시간 단축, 규칙 결합의 효과는 **본 프로젝트의 검증 가설**이다. 국내 최초·한국어 탐지기 부재·분쟁 급증은 주장하지 않는다.

## 슬라이드 2. 검색·생성·탐지와 공간 UI 아키텍처

### 화면 본문

**입력 문서와 답변을 같은 버전으로 연결**

1. **수집·구조화 / 완료 범위**: 공고·첨부, 버전·SHA-256, 파싱·어댑터, SQLite 집계, 근거 청킹
2. **검색·생성 / 연결 예정**: 회사·문서 권한 검사, 원본 BGE-M3 임베딩, PostgreSQL/pgvector, Gemma 답변
3. **검증 / 모델 개발 완료·통합 예정**: 학습한 한국어 토큰 탐지기, 별도 숫자·기간 규칙, 인용 연결 검증
4. **사용자 검토 / 목업 동작**: 의심 구간 표시, 근거 원문, 지도·그래프 노드 선택

- Reality: MapLibre GL JS + OpenFreeMap + 공개 DEM, 건물 extrusion
- Virtual: Three.js, 합성 도시·설비·문서 관계, 카메라 전환
- Live 설계: FastAPI REST + POST NDJSON, 동일 snapshot·답변 해시·문자 좌표
- GraphRAG: 출처를 가진 관계 확장 검색을 후속 구현·평가

### 발표 대본

전체 구조는 데이터 적재와 사용자의 질문 처리로 나눕니다. 먼저 공고 차수와 첨부 해시를 보존하고, 파서 출력에 어댑터를 적용해 집계와 근거 청킹을 수행합니다. 이후 원본 BGE-M3로 검색용 임베딩을 만들고, 서버가 사용자 회사와 문서 권한을 확인한 범위에서 검색하도록 설계했습니다. 답변을 생성한 뒤에는 그 답변과 실제 제공한 검색 문맥을 학습된 탐지기에 함께 넣습니다. 검색용 BGE-M3와 토큰 분류로 학습한 BGE-M3 탐지기는 역할과 가중치가 다릅니다.

숫자·기간 대조는 별도 규칙 모듈로 다룹니다. 탐지기가 근거 조항을 자동으로 정확히 찾아준다고 보장할 수 없어 인용 ID와 원문 연결도 따로 검증합니다. 화면의 현실 모드는 현재 MapLibre이며, Mapbox는 이전 설정 기록입니다. 가상 모드는 Three.js의 합성 장면입니다. 백엔드는 FastAPI와 pgvector, NDJSON 스트리밍을 우선 연결하고, 그래프 관계를 실제 검색에 사용하는 기능은 후속 비교 실험으로 진행합니다.

### 화면 레이아웃 구성안

제목과 상단 설명을 유지하고, 본문에 편집 가능한 좌우 파이프라인을 배치한다. 첫 줄은 수집·구조화, 검색·생성, 답변 검증, 사용자 검토 순이다. 각 상자에 완료·연결 예정·목업 상태를 글자로 쓴다. 두 번째 줄은 Reality/Virtual 공간 엔진과 공통 데이터 계약을 설명한다. 검색과 탐지 노드를 구분하고, 숫자 규칙은 탐지 노드 옆의 별도 항목으로 둔다. 연결선은 최종 목표 흐름을 뜻하며 통합 완료를 뜻하지 않는다고 표시한다.

## 슬라이드 3. 데이터와 탐지 모델 준비 현황

### 화면 본문

**한국어 탐지 모델과 나라장터 적용 데이터를 준비**

**한국어 환각 탐지 / 학습·평가 완료 기록**

- RAGTruth 환각 구간에 `<HAL>` 태그를 붙여 한국어 번역
- 태그 검사 후 문자 위치 재계산, 이진 토큰 분류 학습
- KLUE-RoBERTa, XLM-RoBERTa, BGE-M3 학습
- 숫자 변조는 확인된 취약점. 나라장터 적용 성능은 평가 예정

**나라장터 데이터 / 원본 집계 대조**

- 4~6월 공고 행 137,745건(차수 포함), 최신 차수 124,522건
- 정보시스템 구축·운영 선정, 표본 51건(월별 17건)

| 타깃 분야 | 공고 | 완전 공고 |
|---|---:|---:|
| SW 및 시스템 개발 | 2,163 | 984 |
| 운영 및 유지관리 | 1,313 | 681 |
| 합계 | 3,476 | 1,665 |

완전 공고 = 공고문 + (RFP 또는 과업·규격 문서)

선정 이유: 실적·인력·인증·단가의 검토 적합성. 완비율 1위는 아님.

### 발표 대본

환각 탐지와 적용 도메인 데이터는 두 개의 준비 흐름으로 진행했습니다. 첫 번째는 영어 RAGTruth의 환각 구간에 태그를 붙여 한국어로 번역하고, 태그 검사를 거쳐 문자 위치를 다시 계산한 뒤 토큰 분류기를 학습하는 과정입니다. 프로젝트 기록에는 세 인코더의 학습·평가가 완료돼 있습니다. 그러나 문맥 길이, 임계값, 슬라이딩 윈도우 조건이 서로 달라 이번 슬라이드에서는 성능 숫자를 직접 비교하지 않습니다. 자동 태그 검사도 번역 의미 보존을 입증하는 것은 아닙니다.

두 번째는 나라장터 데이터입니다. 월별 어댑터 보고서의 공고 행은 137,745건이며 최신 차수는 124,522건입니다. 분야 선정에는 파일 실재와 품질 조건을 반영한 워크스테이션 확정 CSV를 사용했습니다. 선택한 SW 개발과 운영·유지관리의 완전 공고 합계는 1,665건이고, 그중 시연 다양성을 고려해 월별 17건씩 51건을 골랐습니다. 이 표본은 모집단의 비례 평가 표본은 아닙니다.

비용은 LLM 호출 전에 Python·SQLite로 가용성과 표본을 정리하고, 선택한 근거 묶음만 전송하는 방식으로 통제합니다. 비용 절감률은 측정하지 않았습니다. 12종은 화면의 겹치는 문서 태그이고, 모든 공고가 12개 파일을 갖는다는 뜻은 아닙니다.

### 화면 레이아웃 구성안

두 열 레이아웃을 사용한다. 왼쪽에는 번역·검사·학습 흐름과 확인된 한계를, 오른쪽에는 공고 모수와 타깃 분야 표를 둔다. 성능과 데이터 건수를 같은 그래프에 섞지 않는다. 하단에는 완전 공고의 정의와 선정 이유를 표시한다. 12종 전체 명칭과 스키마 매핑은 발표자 노트에 둔다.

이전 UI에서는 공간 단계를 L1·L2·L3라고 부르지만, 앞으로 발표와 설계에서는 광역·사옥·설비로 구분하겠습니다. 문서 보안 등급 L1·L2·L3와 이름이 같아도 서로 다른 개념입니다. 화면에 보이는 금액, 기관, 회사 실적과 설비는 합성 데이터입니다. 문서와 설비 ID가 연결되는 상호작용을 구현한 성과이며, 실제 GraphRAG 추론이나 탐지 모델의 판정 결과로 설명하지 않겠습니다.

## 슬라이드 5. 평가 지표와 검증 설계

### 화면 본문

**탐지 성능과 업무 오판을 분리해 측정**

| 평가 축 | 지표·조건 | 현재 상태 |
|---|---|---|
| 환각 탐지 | 환각 P/R/F1, span F1, 숫자 변조 재현율 | 기존 실험 조건 재확인, 공고 평가 예정 |
| 검색·근거 | Recall@K, Hit Rate, 인용 청크 정확도 | 정답 근거 작성 예정 |
| 참가 조건 판단 | 잘못된 충족 판정률, 전체 정확도, 보류율 | 0% 달성 주장 없음 |
| 응답 성능 | 첫 토큰·전체 검증 완료 지연 p50/p95 | 실측 전 |
| 3D·사용성 | 프레임 시간 p95, 60 FPS 목표, 검토 시간·성공률 | 목표·평가 계획 |

- 동일 공고·회사·질문으로 일반 RAG / +탐지 / +규칙 비교
- GraphRAG 관계 확장은 구현 후 별도 비교군으로 추가
- 계획: 질문 300개, 교차 검수 100건, 권한 차단 테스트 20개

### 발표 대본

평가는 환각 탐지, 검색, 실제 업무 판단, 실행 성능을 나눠 진행합니다. 탐지기는 환각 클래스의 정밀도와 재현율, F1을 보고하며, 한국어 구간 경계 평가와 숫자 변조 유형의 재현율도 별도로 봅니다. 검색은 정답 근거가 상위 K개에 포함되는지를 측정하고, 인용이 실제 답변을 지지하는지도 확인합니다.

입찰 조건 오판은 정성 지표가 아니라 정량 지표입니다. 실제로 미충족이거나 자료가 부족한데 충족이라고 답한 비율을 따로 계산하고, 답변 보류율도 함께 보고하겠습니다. 모든 질문을 보류해서 오류만 낮추는 결과를 피하기 위해서입니다. 오류가 관측되지 않더라도 표본 수와 불확실성을 같이 제시하겠습니다.

질문 300개와 교차 검수 100건은 앞으로 수행할 평가 계획입니다. 테스트 질문을 보고 임계값을 고르지 않고 개발용 자료에서 고정한 뒤 평가합니다. 60 FPS도 목표이며, 같은 장비·해상도·장면에서 카메라 이동과 설비 전환 중 프레임 시간을 측정해야 합니다. 아직 응답 지연과 FPS 실측 성과는 없습니다.

### 화면 레이아웃 구성안

표 왼쪽에는 동일 입력과 기준 고정이라는 비교 원칙을 짧게 배치하고, 오른쪽에 지표·조건·현재 상태 표를 둔다. 하단에는 평가할 데이터 규모를 계획으로 명시한다. 측정 전 셀에는 0이나 임의 숫자를 넣지 않고 실측 전·평가 예정으로 표시한다.

### 출처 및 보충 설명

- [업무분담](../../project-docs/팀원별_업무분담_2026-09-12.md), [Live RAG 설계](../../demo-ui/spatial-poc/live-design/Live_RAG_전환설계.md), [학습과정](../../project-docs/학습과정_상세.md)
- 다음 정의는 **발표 초안의 평가 설계 제안**이며 아직 측정 결과가 아니다.
- Recall@K: 질문별 정답 근거 집합 중 top-K에서 찾은 비율의 평균. Hit Rate@K: 하나 이상의 정답 근거를 찾은 질문 비율. K=5, 10을 후보로 두고 평가 전 고정한다.

- 토큰 환각 F1과 macro F1을 구분한다. Span F1은 문자 구간 정확 일치 기준을 먼저 고정하고 중첩 기준 평가는 별도 보고한다.
- 잘못된 충족 판정률: 정답이 미충족·자료부족인 질문 중 충족으로 잘못 판정한 비율. 전체 판정 정확도와 자료부족·보류 비율을 함께 기록한다.
- 규칙만 / 탐지만 / 결합을 같은 숫자 변조·조건 무시 사례에서 비교한다. 규칙은 단위·기준일·기간·AND/OR·예외를 포함해야 하며, 단일 수치 비교를 전체 적격성 판단으로 확장하지 않는다.
- 공고·회사 버전, 모델·프롬프트·임계값, 검색 K, 윈도우 길이·집계 방식을 고정한다. 동종·동일 사업이 개발/평가에 섞이는 누수를 확인한다.
- Latency: 첫 토큰까지와 탐지·인용 검증 완료까지를 분리해 p50/p95 및 실패율을 기록한다. 토큰 길이, GPU, 동시성을 함께 표기한다.

- UI 시인성: 사용자가 의심 구간을 찾고 근거 문서를 열어 올바르게 답하는 과제의 성공률·시간, 색상 외 표식 식별, 키보드 접근, 주관적 읽기 편의(설계한 척도)를 평가한다.

### 발표 대본

다음 단계의 첫 목표는 실제 공고 한 건에서 질문, 검색 근거, 답변, 의심 구간이 같은 버전으로 이어지는 것입니다. 기업 한 곳과 질문 다섯 개부터 검수한 뒤 범위를 넓히겠습니다. 팀원들은 9월 13일까지 요건을 추출하고, 이를 바탕으로 가상 기업 다섯 곳과 질문 300개를 준비합니다. 기업 자료는 실제 회사 내부 자료가 아니라 합성이며, 검수 표에서 충족·미충족·자료부족이 갈리도록 설계합니다.

팀장은 검색과 생성·탐지를 연결하고 UI 담당은 스트리밍 답변, 원문과 노드 강조, 회사 경계와 문서 권한 차단을 검증합니다. 9월 24일부터 라벨링하고 교차 검수를 거쳐 29일 성능을 산출할 계획입니다. 30일 발표 자료와 시연 대본을 정리하고 10월 2일 최종 발표를 진행합니다. GraphRAG와 설비 고도화는 이 기본 연결을 검증한 뒤 확장합니다. 최종 발표에서는 구현된 기능, 측정된 결과, 남은 한계를 구분해 보여드리겠습니다.

### 화면 레이아웃 구성안

템플릿의 세 시점 타임라인을 유지한다. 각 시점 위에는 일정, 아래에는 담당과 산출물·완료 기준을 적는다. 상단 짧은 문장으로 공고 1건의 연결 기준을 제시하고, 하단에는 후속 확장을 배치한다. 설비 모델·Live DB 운영 배포는 일정 확정 전 완료 예정일을 만들어 넣지 않는다.

## 발표 전 반드시 유지할 표현 기준

1. 성능·비용·속도 수치는 원본 실험 조건 또는 집계 산출물이 있을 때만 사용한다.
2. 137,745는 차수 포함 공고 행, 124,522는 월별 최신 차수 합계다. 연간 시장 규모나 서로 다른 실제 사업 수로 바꾸지 않는다.
3. GraphRAG·서버 권한·실제 Q&A는 통합 완료로 표시하지 않는다.
4. 공간 단계는 광역·사옥·설비, L1/L2/L3는 문서 보안 등급으로 설명한다.
5. 합성 자료·UI 예시를 모델 추론 결과나 실제 기업 증빙으로 소개하지 않는다.
6. 60 FPS·오류 최소화·검토 시간 단축은 검증 목표다. 100% 탐지·오판율 0% 달성·번역 손실 0을 쓰지 않는다.
7. 원천 문서, 모델 가중치, API 키를 발표 저장소에 추가하지 않는다.
