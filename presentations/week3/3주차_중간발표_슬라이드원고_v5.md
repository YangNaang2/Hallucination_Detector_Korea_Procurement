## 슬라이드 2. 입찰 제안팀에는 답변 검증과 문서 보호가 함께 필요하다

### 화면 본문

대상: 정보시스템 구축·운영 입찰을 준비하는 기업의 제안팀

| 추진 배경 | 발표할 내용 |
|---|---|
| 문서 근거가 있어도 생기는 오류 | RAG 답변에도 근거 없는 내용·모순이 남을 수 있다. 자격·실적·기간을 원문과 대조해야 한다. |
| 서로 다른 공개 범위의 자료 | 공개 RFP와 사내 실적·인력·원가를 함께 검토한다. 회사·프로젝트·승인 조건에 따라 검색 범위를 제한한다. |
| 왜 나라장터 RFP인가 | 공개 공고를 확보할 수 있고, 자격요건과 기업 증빙을 대조하는 업무 흐름이 분명하다. |
| 왜 사내 실행을 지향하는가 | 민감 자료의 처리 경계를 통제하고, 로컬 서버 자원에 맞는 모델 구성을 검토한다. |

### 발표 대본

입찰 제안팀은 공고의 자격요건을 읽고 회사 실적과 인력 자료를 대조합니다. RAG로 관련 문서를 제공해도 답변에 근거 없는 설명이나 원문과 모순되는 내용이 생길 수 있다는 점은 RAGTruth 연구에서도 확인됩니다. 따라서 저희는 답변을 자연스럽게 만드는 것에 더해, 어떤 구절을 다시 확인해야 하는지 보여주려 합니다.

이 업무에는 공개 공고와 비공개 회사 자료가 함께 등장합니다. 답변이 문서에 부합하더라도 질문자가 그 문서를 볼 권한이 없다면 적절한 결과가 아닙니다. 그래서 검색 전에 회사와 프로젝트, 승인 조건을 확인하는 구조가 필요합니다. 사내 실행은 민감 자료의 처리 범위를 통제하기 위한 프로젝트의 운영 목표이며, 현재 폐쇄망 운영을 검증했다는 뜻은 아닙니다.

### 화면 레이아웃

두 열로 정리한다. 위쪽 왼쪽은 환각 문제, 오른쪽은 접근 권한 문제다. 아래쪽에 RFP 선정 이유와 사내 실행 이유를 각각 연결한다. 별도 성능 비교 차트와 평가지표는 사용하지 않는다.

### 근거와 편집 판단

사용자 첨부 `추진배경_타겟팅_배경설정.md`의 RFP 전환, 제안팀 페르소나, 조건부 접근, 사내 처리 방향을 반영했다. 다음 문구는 근거가 충분하지 않거나 팀공유 7절과 충돌하여 사용하지 않았다: 도구가 전무하다는 주장, 모델 성능과 환각률의 보편적 관계, 외부 API 전송이 항상 위법·형사책임이라는 단정, 실측되지 않은 CPU 지연 시간. 첨부 문서의 법률·정부 가이드북 해석을 인증 또는 준수 실적으로 확대하지 않았다.

RAG에서도 근거 없는 주장이나 모순이 발생할 수 있다는 설명은 [RAGTruth, ACL 2024](https://aclanthology.org/2024.acl-long.585/)의 연구 범위에 한정한다. 조달 분야의 성능이나 피해 증가율로 해석하지 않는다.

## 슬라이드 3. 한국어 환각 탐지와 권한 기반 RAG 전체 구조

### 화면 본문

첨부 SVG의 두 트랙을 유지하고, 발표용으로 간추린 [전체 구조도](source/보안RAG_전체구조_발표용.svg)를 화면 전체에 배치한다.

| TRACK A: 학습 파이프라인 | TRACK B: 질의 처리 목표 구조 |
|---|---|
| RAGTruth 원본·환각 구간 확보 | 회사·프로젝트·승인 조건 확인 |
| 한국어 번역·태그 검사 | 허용된 문서 안에서 근거 검색 |
| 한국어 라벨 좌표 재계산 | 인가 문맥으로 로컬 답변 생성 |
| 인코더 모델 학습 완료 | 문서 지지 여부와 수치 조건 검토 |
| 서비스용 탐지기 연결 예정 | 근거 원문과 의심 구간 함께 표시 |

TRACK A에는 학습 완료와 서비스 연결 예정, TRACK B에는 목표 구조와 실제 통합 예정 상태를 표시한다. 학습한 가중치를 질의 처리의 탐지 단계에 연결하는 선을 유지한다.

### 발표 대본

전체 구조는 두 트랙입니다. 왼쪽은 질문이 들어오기 전에 탐지기를 준비하는 과정입니다. RAGTruth의 환각 구간을 태그로 감싸 번역하고, 한국어에서 달라진 문자 위치를 다시 계산해 토큰 라벨을 만듭니다. 여러 인코더의 학습은 완료된 상태이며 서비스에 사용할 모델과 처리 조건을 고정해 연결해야 합니다.

오른쪽은 사용자가 질문했을 때의 목표 흐름입니다. 먼저 서버가 문서 접근 조건을 검사하고, 허용된 자료에서 근거를 검색합니다. 생성 모델은 그 근거로 답하고, 탐지기는 같은 근거와 답변을 비교합니다. 숫자와 기간 비교는 별도 규칙으로 처리합니다. 마지막으로 사용자는 의심 구간과 원문을 함께 확인합니다. 오른쪽의 실제 인증·인가와 검색·생성·탐지 통합은 다음 단계의 작업입니다.

### 화면 레이아웃

첨부 SVG의 어두운 배경, 파란 학습 트랙과 분홍 질의 트랙, 단계 번호와 화살표를 유지한다. 세부 문장을 단계별 두 줄로 축약해 글자를 키운다. 전체 구조 설명에 집중하고, 권한 예시는 5페이지, 실연결 기술은 6페이지로 분리한다.

### 구조도 수정 기록과 근거

원본: 사용자 첨부 `gemini-svg.svg`. 발표용 파생 SVG만 저장소에 포함한다. 원본 첨부 파일은 변경하지 않았다.

원본에 포함된 F1 수치, 번역 손실 없음, 태그 통과율, CPU 지연 실적, KLUE 최종 확정, 외교부 표준 완벽 대응, 외부 통신 차단 완료 등의 표현을 제거했다. 단순 개인 등급 필터를 회사·프로젝트·승인 조건 검사로 고쳤다. 학습한 BGE-M3 탐지기와 검색용 원본 BGE-M3를 구분했다.

## 슬라이드 5. 프로젝트 목표와 비취인가 개념의 적용 범위

### 화면 본문

목표: 입찰 담당자가 허용된 자료로 조건을 검토하고, 답변의 의심 구간을 원문에서 확인한다.

| 자료 등급: 프로젝트 예시 | 보호할 내용 | 접근 조건 설계 |
|---|---|---|
| L1 공개 | 공고문·RFP·과업 문서 | 공개 문서 열람 |
| L2 대외비 | 회사 실적·인력·인증 | 회사 일치 + 프로젝트 배정 + 문서 권한 |
| L3 기밀 | 원가·투찰 전략·마진 | L2 조건 + 해당 자료 승인 + 유효기간 |

- 비취인가 = 비밀취급인가
- 발표의 L1~L3는 사내 문서 분류 예시다. 국가 비밀 등급·인가 취득을 뜻하지 않는다.
- 등급은 데이터에, 접근은 요청 조건에 있다.
- 높은 직급이어도 다른 프로젝트는 거부하고, 배정·승인·유효기간을 충족하면 필요한 자료를 허용한다.

### 발표 대본

저희가 궁극적으로 제공하려는 것은 허용된 자료에 근거한 입찰 검토 보조입니다. 자료를 보여줄 수 있는지 먼저 확인하고, 그 범위 안에서 생성한 답변에 근거가 있는지 검토하도록 돕습니다. 최종 입찰 판단은 담당자가 근거와 조건을 확인한 뒤 내립니다.

첨부 자료의 비취인가는 비밀취급인가를 가리키지만, 이번 프로젝트에서 사용하는 L1·L2·L3는 사내 문서 분류를 위한 예시입니다. 국가 비밀 등급이나 실제 인가 취득과 동일하게 소개하지 않습니다. 구현하려는 권한 모델은 직급만으로 문서를 여는 방식이 아니라, 회사 경계와 담당 프로젝트, 자료별 승인 및 유효기간을 요청마다 확인하는 방식입니다. 예를 들어 같은 실무자라도 특정 프로젝트 승인을 받으면 필요한 자료를 볼 수 있고, 임원이라도 다른 프로젝트의 자료는 권한이 없으면 거부합니다. 실제 인가 기능은 아직 구현 예정입니다.

### 화면 레이아웃

상단에 프로젝트의 한 문장 목표, 중앙에 자료 등급·내용·접근 조건의 편집 가능한 표를 둔다. 하단 왼쪽은 용어 구분, 오른쪽은 직급과 무관한 조건부 접근 예시다.

### 근거와 적용 범위

첨부 추진배경 MD 4절, [Live 설계의 access_grants와 권한 정책](../../demo-ui/spatial-poc/live-design/Live_RAG_전환설계.md), [나라장터 문제정의 문서의 비밀취급인가 구분](../../project-docs/나라장터_문제정의_1차리서치_팀원용.md). 법정 용어 참고: [국가법령정보센터 보안업무규정](https://www.law.go.kr/법령/보안업무규정). 법적 인증·표준 준수·기관 승인 실적을 주장하지 않는다. 첨부 MD의 승인·유효기간 조건을 이번 발표 설계에 반영했으며, 이것이 기존 코드 구현 완료를 뜻하지 않는다. L2/L3 기업 자료는 합성 데이터로 준비한다.

## 슬라이드 6. 한 질문에서 근거·권한·의심 구간을 연결하는 방식

### 화면 본문

설계 단계: 질문 + 공고 버전 + 회사 자료 버전을 하나의 요청으로 고정

1. **권한을 먼저 확인:** 회사·프로젝트·승인 조건, 허용된 청크만 검색
2. **근거로 답변 생성:** 원본 BGE-M3 검색, 인가 문맥으로 Gemma 생성, 탐지기도 같은 문맥 사용
3. **검토 결과 표시:** 학습 탐지와 규칙을 분리하고 원문·인용 위치를 연결, 자료 부족 시 판단 보류

Live 연결 설계: FastAPI REST + POST NDJSON, PostgreSQL/pgvector, 청크 ID·문서 해시, 원문·다운로드·그래프에도 같은 권한 적용.

GraphRAG의 후속 역할: 요건과 증빙의 관계를 따라 검색 후보를 확장하고, 확장된 노드에도 같은 권한을 검사한다. 현재 관계 검색은 실제 서비스에 연결되지 않았다.

### 발표 대본

전체 구조에서 실제 연결 시 맞춰야 하는 것은 권한과 버전입니다. 회사나 공고를 바꿨는데 이전 질문의 답변이나 다른 기업의 근거가 남으면 안 됩니다. 따라서 공고와 회사 자료 버전을 고정하고, 서버가 허용한 청크를 생성 모델과 탐지기에 동일하게 전달하도록 설계했습니다.

검색용 BGE-M3 임베딩과 학습한 환각 탐지기는 서로 다른 역할입니다. 탐지기는 입력 문서에 대한 지지 여부를 판단하며, 숫자·기간의 조건 비교는 별도 규칙에서 다룹니다. 원문 인용은 청크 ID와 위치 정보로 연결하고, 자료가 부족한 질문은 판단을 보류하도록 설계합니다. GraphRAG는 요건과 증빙 관계를 따라 근거 후보를 확장하는 후속 기능입니다. 화면에서 보이는 관계 그래프만으로 이 검색이 구현됐다고 설명하지 않겠습니다.

### 화면 레이아웃

위쪽에 편집 가능한 세 단계 구조도를 가로로 배치한다. 아래 왼쪽은 Live API와 데이터 연결, 오른쪽은 GraphRAG 후속 범위다. 평가지표·성능 수치는 넣지 않는다.

### 근거와 기술 보충

[Live RAG 전환 설계](../../demo-ui/spatial-poc/live-design/Live_RAG_전환설계.md), [contracts.ts](../../demo-ui/spatial-poc/live-design/contracts.ts). 저장 구조의 문서 버전·SHA-256, 청크의 페이지·절·문자 위치, 접근 권한, 답변 실행 기록을 연결하는 설계다. 원문 뷰어·다운로드·그래프·캐시·LLM 컨텍스트가 같은 권한 정책을 따라야 한다. 클라이언트 필터만으로 인가를 구현했다고 하지 않는다. 개인정보 마스킹이나 불변 감사 로그도 현재 완료 기능으로 추가하지 않는다.
